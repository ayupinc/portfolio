# Maple Intel Visual and Editorial Style Guide

## Status

Design direction, not a finished design system. Exact typefaces, colour values, spacing tokens and components should be selected only after testing real page content and work imagery.

## Creative direction

The visual character should be:

- considered;
- technically competent;
- quiet;
- editorial;
- spacious;
- evidence-led.

The work should attract attention before decorative brand elements. Layout and typography should make dense technical subjects feel ordered rather than simplified.

## Visual hierarchy

Use hierarchy to distinguish:

1. operational question or proposition;
2. outcome or central idea;
3. supporting explanation;
4. technical evidence;
5. metadata and detail.

Do not give headings, tags, cards and calls to action equal visual weight.

## Typography

Direction:

- a highly legible, restrained sans serif for primary interface and body text;
- optionally, a complementary editorial face used sparingly for selected display text;
- clear differentiation between prose, labels, captions and code;
- comfortable line length and generous line spacing;
- tabular numerals where metrics need comparison.

Avoid:

- futuristic “technology” typefaces;
- excessive weights;
- very light body text;
- oversized headings that displace the work;
- long centred paragraphs.

Typeface selection remains open until representative pages are composed.

## Colour

Use a neutral foundation with a limited Maple-derived accent system.

The palette should support:

- high-contrast body text;
- quiet surfaces for technical content;
- one controlled primary accent;
- semantic colours for status or data only when meaning requires them;
- charts and diagrams that remain distinguishable without relying solely on colour.

Muted does not mean low contrast. All text, controls, focus states and data graphics must remain accessible.

Exact palette values are deliberately undecided pending review of the current Maple Intel identity and representative report screenshots.

## Imagery

### Primary imagery

- Power BI report interfaces;
- data and semantic models;
- SQL/data-flow diagrams;
- operational workflow illustrations;
- annotated analytical details.

### Treatment

- crop deliberately around the point being discussed;
- preserve enough interface context for authenticity;
- use consistent framing and corner treatment;
- avoid ornamental device mockups unless they clarify scale or use;
- provide captions;
- consider separate mobile crops;
- retain readable labels whenever the text is part of the evidence.

### Do not use

- stock photographs of meetings or people pointing at screens;
- abstract “data network” imagery;
- fake metrics;
- generic illustration merely to fill space;
- visual assets that imply a team or office that does not exist.

## Diagrams

Diagrams should explain structure, flow, state or lineage.

Use:

- a small, consistent shape vocabulary;
- explicit direction;
- short labels;
- restrained colour;
- legends only when necessary;
- text alternatives for essential meaning.

Avoid diagrams that are simply decorated lists.

## Layout

- Use generous whitespace to group ideas.
- Prefer clear editorial sections over a wall of cards.
- Let case-study layouts vary when the evidence requires it while retaining consistent navigation and typography.
- Design desktop views to present technical assets strongly.
- Treat mobile as a deliberate reading experience, not a compressed desktop page.
- Avoid horizontal scrolling for essential content.

## Components

Likely components include:

- global header and navigation;
- proposition/intro block;
- case-study preview;
- capability group;
- evidence figure with caption;
- case-study metadata;
- process or lineage diagram;
- technical detail panel;
- related-work links;
- contact prompt;
- footer.

Components should emerge from approved content rather than dictate it.

## Motion

Motion is optional and should only:

- explain a state change;
- preserve orientation during navigation;
- provide restrained interaction feedback.

Avoid:

- scroll-driven spectacle;
- animated counters;
- automatic carousels;
- parallax;
- movement that competes with report imagery.

Respect reduced-motion preferences.

## Editorial mechanics

### Headings

Use sentence case. Prefer informative headings over labels such as “Solutions” or “Innovation”.

### Paragraphs

Keep opening paragraphs concise. Longer technical explanation is appropriate when structured with descriptive headings and figures.

### Lists

Use lists for genuinely parallel information, not to avoid writing a coherent explanation.

### Links and actions

Use descriptive language:

- View the queue-monitoring case study
- Explore the modelling approach
- Contact Stephen

Avoid:

- Learn more
- Click here
- Discover now

### Technical terms

Use established terms accurately. Expand uncommon acronyms on first use. Do not remove necessary technical language merely to sound accessible; explain it in context.

## Accessibility baseline

The future implementation should target WCAG 2.2 AA and include:

- keyboard-operable navigation and interactions;
- visible focus styles;
- semantic heading order;
- sufficient colour contrast;
- useful alternative text and captions;
- labelled forms with clear errors;
- no essential information conveyed by colour alone;
- responsive text without loss of content;
- support for reduced motion;
- accessible diagrams or equivalent explanations.

## Design review questions

For every page or component, ask:

1. What does the visitor need to understand here?
2. What evidence supports it?
3. Is the technical work receiving the visual emphasis?
4. Can a scanning reader find the central point?
5. Can a technical reader inspect enough detail?
6. Is anything present merely because portfolio templates usually contain it?
