Cisco Telephony

Context

After a switchboard change, the existing third-party call reporting tables became unreliable with missing information. A fix was required to restore operational reporting, but the table construction was too opaque to repair so a new solution was required.

What I Did

I built a new telephony model from native Cisco event data, where I translated low-level call and agent events into analytical tables holding calls, agent calls, sessions and activity data. I applied classification to each event, reconstructed the agent sessions, attributed events temporally to the sessions and applied agent ownership logic to the calls to enable the data to be used consistently for reporting.

Data Engineering Process

I worked from the native Cisco tables, which held one row per record for routed calls and one row for each segment of each call, all joined by a common key. I analysed combinations of call types and dispositions to identify which rows represented routing, ringing, answering, talking, transfer, monitor and other internal call behaviour, allowing call segments to be classified before aggregation.

The challenge was that Cisco records the call lifecycle as multiple independent events rather than a single transaction, so the meaning of each record had to be inferred from the information within it before the call could be reconstructed accurately. Using a complex stored procedure, I was able to do this and create a new call table for all call analytics across the organisation.

An anonymised example of the SQL script is available here.

Agent events were also derived from the third-party tables and needed recreating. Cisco stored agent activity as individual events which were often fragmented over consecutive reporting intervals rather than as complete sessions or activity periods. I reconstructed the login, logout and status events into continuous analytical sessions and activity periods, which meant calls and activities could be analysed together within an individual agent session.

Calls attributed to agents were captured from the new calls table and where attribution was unclear, particularly for internal, transferred and monitored calls, I applied ownership rules to assign each side of the call to the appropriate agent perspective. This allowed agent calls to also be included per session to give a clear attribution of activity per agent on every logged-in session, even if only one call record existed.

I validated the outputs against Cisco interval reporting, existing reports and agent activity to make sure reconstructed calls, sessions and activities reflected operational behaviour.

I also applied the same procedure and table structure to another switchboard which had no call or agent-level reporting tables. This switchboard had more complex routing plans for internal as well as external calls, which made the attribution more challenging.

Outcome

The output was a reusable telephony analytics model consisting of call, agent call, session and activity tables which became the shared reporting layer for telephony reporting across the organisation. The model not only replaced the existing tables but also introduced detailed agent session-level data and provided call-by-call reporting for both switchboards.

All telephony and agent reports in the organisation moved to the new model, providing an accurate single source of truth for telephony metrics supporting call-level answer and abandonment metrics with handling and wait times, demand analysis, staff workforce planning and agent-level performance reporting.
