Questionnaire Responses

The questionnaire system is built into the case management system and is used to prompt questions and capture responses in telephone assessments. Local technical teams create the question and response flow in a module and make them available to use in the call. Data includes question text, responses, outcome codes and timestamps, and is stored as one row per question response rather than one row per assessment episode. A single questionnaire completion could produce dozens of rows. There are multiple questionnaires, each with different structures and branch pathways used by different clinical teams.

The data also carried quality problems inherited from its collection context. Free-text responses were inconsistently formatted, response categories existed under multiple spellings and variations, and question text differed across questionnaire versions covering the same clinical concept. None of this could be resolved inside a report; it required a dedicated transformation layer built before any reporting logic was applied.

What I Did

  • Designed and built the full T-SQL transformation pipeline from raw questionnaire source data to reusable reporting tables
  • Authored the episode view, response cleaning stored procedure and classification logic consumed by Power BI dashboards
  • Created stable questionnaire episode keys and episode-in-call sequencing where the source system held no completed assessment entity
  • Identified a branch loop-back issue and replaced max-based branch selection with row-number logic to capture the first selected pathway
  • Investigated questionnaire re-open behaviour and built detection flags so duplicated timestamps did not distort duration calculations
  • Standardised question text, response text and response categories so reporting could aggregate across questionnaire versions

Data Engineering Process

The first stage was episode identification. The source table held no persistent identifier representing a completed questionnaire attempt, so one had to be constructed. An episode key was derived from the incident identifier, questionnaire set identifier and run number within the incident. This produced a key that was both human-readable and sortable, making it practical for use in downstream reports and investigations. A separate derived field ranked each episode within the incident using a dense rank over start time, providing an episode-in-call sequence useful for tracking activity across a single call.

Branch identification required particular care for questionnaire sets where clinicians navigate different pathways depending on the type of call. The branch name was extracted from the response to the pathway selection question, but a construction issue in one questionnaire set created a loop back to other questionnaire sets, overwriting the branch timestamp with a later time. The logic was changed to use a row number ordered by the earliest response time rather than the latest, ensuring the branch captured was always the one first selected rather than the last.

A further edge case arose from how the system handles questionnaire re-opening. When a clinician reopened a completed questionnaire to amend responses, a new instance with an incremented run number was created but copied the original response timestamps into it. This made the new instance appear to have started much earlier than it actually did, distorting duration calculations. Detection logic was built to identify sessions sharing the same incident, questionnaire set, branch and start time, flagging the earlier instance as a potential donor and the later as a re-opened episode. This gave reporting the means to exclude or caveat re-opened sessions without silently distorting duration figures.

Response normalisation and text cleaning addressed the variation in how responses had been recorded across questionnaire versions and clinical teams. Mapping logic assigned consistent question identifiers and clean question text to each response, making aggregation across questionnaire versions reliable. A cleaning pass standardised free-text responses before classification was applied, and responses that could not be mapped to a category were flagged explicitly rather than silently dropped, so coverage could be monitored and improved over time.

Output Model

The engineering process produced two analytical tables:

  • An Episodes table, with one row per completed questionnaire episode, generated episode key, episode sequence within the call, questionnaire set, branch, start and end timestamps, duration, and donor and re-opened flags
  • A Responses table, with one row per cleaned and classified response linked to the episode key, consistent question identifier, clean question text, clean response text and assigned response category

Downstream Power BI reporting was built against these two tables rather than the raw source. Clinical quality reporting, outcome analysis and pathway monitoring could all operate against a stable, consistent structure without reproducing the cleaning and classification logic independently in each report.

Outcome

The transformation layer made structured questionnaire reporting possible for the first time. Where previously the raw data could only be queried at the individual response level, clinical teams could now analyse completed assessment episodes, track questionnaire activity within a call, and aggregate responses to the same clinical question across different questionnaire versions without the results being contaminated by version differences or re-opened sessions.

The branch correction and re-open detection work uncovered source data behaviours that had not been documented and were actively distorting any analysis that had been attempted against the raw tables. By surfacing these as explicit flags in the output model rather than silently filtering them, the reporting layer remained auditable, and the underlying issues were visible to anyone investigating unusual figures.

The Episodes and Responses tables became the shared analytical foundation for clinical quality, outcome and pathway reporting, with all cleaning and classification logic centralised in the transformation layer rather than replicated across individual reports.
