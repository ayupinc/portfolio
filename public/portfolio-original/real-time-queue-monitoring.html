Real-Time Clinical Queue Monitoring and Operational Wallboard

Near-live queue visibility for outbound call-back work, designed for continuous operational use by team leaders.

What I Did

  • Built status reconstruction logic from multiple audit events to show each case's current operational state
  • Created near-live queries into the case management system to gather queue and workload data
  • Designed a lightweight DirectQuery semantic model for continuous operational reporting
  • Developed DAX measures for queue volume, active workload, elapsed time and longest-waiting case reporting
  • Designed and built a wallboard layout optimised for continuous display by operational teams
  • Implemented bookmark navigation between queue views and drill-through to case-level detail
  • Produced metric definitions and support information for operational governance

Context

I developed this wallboard for a high-volume section of a contact centre performing outbound calls to follow up on earlier inbound conversations. Cases waited in a backlog and were called when an agent was available, with different call types reflecting priority and several teams holding different operational skills.

The operational challenge was live visibility. Team leaders needed to understand how many cases were waiting, which priorities were building, which work was already active and where the longest waits were occurring without relying on delayed extracts or manual checks.

Technologies were T-SQL for the warehouse and native source tables, with Power BI DirectQuery for the semantic model, DAX measures and reporting canvas.

Key Reporting Challenges

  • Reconstructing a live queue state from audit events rather than a single current-status field
  • Showing waiting demand and active workload clearly enough for continuous operational monitoring
  • Keeping the semantic model lightweight enough for DirectQuery performance
  • Calculating elapsed waiting and active durations in a way that updated with current time
  • Supporting both wallboard visibility and drill-through investigation from the same report
  • Separating priority, queue and team views without creating multiple disconnected reports

Queue State Reconstruction

Case details were held in the case management system tables, but the queue state had to be inferred from a series of audit events showing movement between queues, entering or exiting the queue and starting or ending a call-back. It could not be read from a single status field.

I wrote reconstruction logic that interpreted those events into a single observable state for each case so the wallboard could report live waiting demand, active work and priority position consistently. This followed the same principle as the wider queue activity model: isolated audit records were transformed into operational states that users could understand and act on.

The logic also needed to handle cases moving between queues, cases returning after earlier activity and records where the operational meaning depended on the sequence of surrounding events. Preserving that interpretation in the data layer kept the Power BI report focused on presentation and operational decision support rather than repeating complex event logic inside visuals.

Semantic Model and Measures

The semantic model was intentionally kept lightweight. A single operational fact table, populated by a near-live SQL extraction process, carried queue, status, elapsed-time and clinician fields. Small lookup dimensions handled priority labels and queue classifications.

DirectQuery was used throughout so the wallboard reflected current operational state rather than a cached snapshot. Despite the complexity of the operational logic, the extraction query consistently executed in under one second.

DAX measures were focused on operational state rather than historical analysis. They covered live queue volumes, active workload, active clinician counts, longest waiting case by priority and elapsed duration measures for both waiting and active work. These measures allowed the same model to support headline wallboard tiles, priority breakdowns and drill-through investigation without separate calculations for each page.

Wallboard Design

The Power BI solution was designed as a wallboard rather than a traditional analytical report. The first design priority was at-a-glance readability for team leaders monitoring demand continuously during operational shifts.

The dashboard provided live waiting volumes, active workload, longest waiting case by priority, longest active assessment duration and active agent counts by role. Visual hierarchy was kept deliberately simple so queue pressure, waiting time and active work could be understood quickly from a distance.

Additional functionality included drill-through into detailed case-level records, bookmark navigation between queue types and metric definitions with support/version information for governance. This allowed the same report to work both as a shared operational display and as an investigation route when a team leader needed to understand the cases behind a metric.

Outcome

The wallboard was deployed for continuous 24/7 operational use across all teams and became the primary operational view of live queue demand across the organisation.

It gave operational leaders a shared view of current workload, active activity and waiting pressure, replacing manual checks with a continuously available source of queue information. By combining event reconstruction, DirectQuery modelling and wallboard-focused design, the report supported immediate operational decision making while retaining drill-through detail for case-level review.
